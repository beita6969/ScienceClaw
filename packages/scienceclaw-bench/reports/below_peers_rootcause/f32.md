## 0. 结论
- 工具: 新增 `scilib.hippo_unet` —— **从零训练**(无预训练权重)的 4 级 3D U-Net 集成(默认 3 个网络, 2500 迭代, CE+soft Dice, GPU 仿射/强度增广, 7 次平移 TTA, 训练后接 `hippo.postprocess`)。沙箱里没有 torch, 所以训练/预测走文件中转桥到 Node0015 的 GPU 2(与 FoR30/36/51 同一座桥, 白名单加了 `hippo_unet.{fit_unet,predict_unet,predict_proba,fit_predict}`; 模型句柄必须是 fit 返回的主机路径)。

## 1. 为什么加这个工具(根因)
上一轮 FoR32 只能用经典流程(patch 标签融合 + LightGBM 体素分类), 因为沙箱没有 torch; 同行都是 3D 卷积网络。U-Net 需要 GPU 训练, 28 个训练体足够小, 一次训练只需约 44 s/网络。通过桥调用服务器 GPU, 和其他学科的做法一致。

## 2. 工具与 dev 选型(只用 28 训练体 → 8 dev 体, 均为 dev, 没读 id/ood)
- 架构/增广/损失/TTA 见模块文档字符串(agent 可见文档只写事实: 函数、参数、结构、实测耗时, 没有阈值/边际/"应该用什么"的配方)。
- dev 扫描(8 体, 噪声大): 300 迭代×1 网络 0.8412; 默认(2500×3, TTA) **0.8659**; 默认不用 TTA 0.8651; 1000×3 0.8629; 2500×1 base=24 0.8645。差异在噪声内, 保留默认。
- 测试: `tests/test_remote_blobs.py` 新增 3 个(桥路由、模型路径必须来自主机、CPU 小规模训练/预测); 全量相关测试通过。

## 3. Agent 端到端 episode (`runs/toolon_f32_id`) —— z=0
| 项 | 值 |
|---|---|
| primary(16 体 DSC) | 0.8630(参考图谱 0.7271, 验收线 +0.03 → **accepted=True**) |
| completed / reproducible / hard_ok | True / True / True |
| 策略 token(逻辑) | **204,297 > 200,000 → within_budget=False → z=0**(stop=token_budget, 20 步, 墙钟 2393 s) |
- 轨迹: 步 3 旧工具 dev 0.8383; 步 4–5 默认 U-Net dev 0.8659(比旧工具高); 步 7–8 已经生成并**提交**了默认 U-Net 的 16 体预测; 之后 agent 继续扫配置(5 网络 0.8665、base24 0.8658、5000 迭代 0.8699、5 网络×5000 迭代 0.8700), 步 16 把提交换成 5000 迭代版, **步 19 再加一个约 445 s 的 5×5000 评估节点, 这一步的回复让累计 token 从 189k 到 204k**。
- 判定规则(`docs/DESIGN.md` decision 7, 也逐字写进了 agent 的提示词 `_FINISH`): val/eval 模式只看"最后一个 y 被算出来的步", 预算用那一步结束时的累计 token 计。步 19 的 add_node 没有改变提交(y 仍由步 16 的节点产生), 但它是"最后一个 y 已算出的步", 所以用它的 token 计数。步头里已经给了 `policy_tokens_left=10000`、`last_reply_tokens=13000`, agent 仍然发起了一次 15k token 的回复, 没有用 `finish`。
- **我不改这条规则, 也不放宽预算, 也不因此重跑挑选**。这是 agent 的预算管理问题(同样的现象出现在 FoR51 try3, 211k)。若之后要提高通过率, 合规的方向是(a)让进化出的 Skill 学会"已提交且提升 <0.005 就 finish"(这是论文方法里该由 Skill 进化学到的东西), 而不是手写提示词配方。

## 5. 披露
- **没有预训练**: U-Net 从零训练, 只用 28 个可见训练体。没有 MSD/Hippocampus 的预训练权重, 不存在预训练数据重叠(不同于 FoR36 的 htdemucs、FoR47 的 Stanza、FoR51 的 CHGNet)。
- **ood 是强度编码代理**(uint8 0–255 / float ~1e5 的重编码), 不是真正的分布外; 每体先做稳健强度归一化, 所以 ood 与 id 相当是设计上的结果(旧工具同样)。
- 仅 tool-ON; 没有新做"关工具"对照(旧工具 `hippo` 的数字只是历史工具版本的对照, 不是关工具基线)。
- 1 个 episode, z=0, 如实记录。

## 6. 剩余
- 与 nnU-Net 的差距主要来自训练体数量(28 vs 208–260)与协议; 进一步提升需要更多训练数据或预训练, 我们的可见数据只有这些。
- episode 层面的预算纪律 → 留给 Skill 进化/后续尝试。

## 7. 带 U-Net 工具的 Skill/Operator 进化试验(3 轮, `configs/toolon_evo_f32.yaml`)
标注: [实测]。只有 tool-ON; 种子 20260928; n_val=2, 3 轮; 桥已打开(`SCIENCECLAW_REMOTE_SPOOL`)。run: `runs/toolon_evo_f32-20260930-115027`。

**结果: 3 个候选全部未被采纳, 3 个快照 A_1/A_2/A_3 与 A_0 完全相同, 因此没有做 A_0 vs 最终快照的 id/ood 对比(没有差异可比)。**
- 候选只含 Operator, **没有 Skill**: 三个 source episode 都是 z=1(source 模式取 solver 的"最后一个通过的验证证据", 步 19/14/10, 不计之后的超预算步), 没有"先失败后成功"的对照, 按 Eq. 9 不形成 Skill(`skill_log.reason = no replay-verified failure e- before e+`)。
- 三个候选的 Operator 都卡在 R_src(Eq. 13: 对 source episode 用候选程序**重新做一遍**, 所有新 Operator 都必须出现在通过的证据图里并成功运行): c0001 Pass=True 但 Use=False(3 个 Operator 一个都没被用), c0002 重解没有通过, c0003 Pass=True 但 Use=False。提示里确实给出了 Operator 卡(`# Operators from your library`), agent 仍然全用自己写的 code 节点, `uses` 全空。与 overnight 的 37 个候选同一现象(operators unused in source replay)。
- 我没有改 R_src、Use、门槛或预算来"凑"一个被采纳的候选。

**更正(重要)**: 我在进度里曾把 A0 val 的 z=0 说成 token 超预算(355k), 其实 355,535 是两个 episode 的合计。**逐个看, 每个 val episode 只用了约 178k token(在 200k 内), 是墙钟超了**: agent 墙钟 2607 s / 2511 s > 该学科的 `max_wall_s=2400`(stop=wall_budget; primary 0.871 / 0.885, completed 且 accepted)。墙钟主要来自 agent 自己反复起 5–8 个网络的大集成节点(单节点 440–600 s, 600 s 是节点上限), 而不是 LLM 调用(policy_wall 约 200 s)。所以 FoR32 带 U-Net 的失败模式是"提交后继续花大算力精调", 与 token 超支同根。
- 第一次(桥没开, agent 只能用旧 `hippo`)的 A0 val 是另一回事: 两个 episode 合计 414,637 token(每个约 207k > 200k), 两个都 z=0; 该 run 保留为 `runs/abandoned_toolon_evo_f32_nobridge-20260930-110907` 作披露, 不参与结论。

**含义(给"进化能否学会 finish"这个问题)**: 在当前的 source/val 分工下, source 模式对"提交后继续精调"不扣分(取最后通过的证据), 只有 val/eval 模式才会因超预算判 z=0, 所以进化这条路看不到这种失败, 无法挖出"见好就收"的 Skill。这是评测口径的结构性事实, 不是调参能解决的。要让进化看见它, 需要把 source 模式的通过判据改成和 val/eval 一致(计入最后一个 y 的预算), 这会改变 DESIGN 的 source 语义, **我没有动, 留给你决定**。
