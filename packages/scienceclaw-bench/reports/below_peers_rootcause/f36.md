# FoR36 (MUSDB18 四声部分离): 为什么明显低于同行, 以及能调用哪些同行工具 (NAME=f36, 2026-09-30)
标注: [测]=我在磁盘数据上测量; [源]=引自来源; [估]=估计. 16-item 切片噪声 SD 约 0.5 dB(oracle)/0.76 dB(mixture 参考) [测], 单个 episode 之间 <1 dB 的差异不算显著.

## 1 ROOT CAUSE (量化)
**结论: 没有 bug; 是 capability + 设计问题.** 沙盒里没有预训练分离器, 每个 episode 只有 8 条 6 秒有标注摘录; 工具箱 (LightGBM 软掩码) 在这种数据量下饱和在约 3 dB; agent 又在第一次 dev 打分后就早停. 协议 (22.05 kHz, 6 秒, 16 条) 并不压低天花板.
- 现状 [测, 读 result.json]: id 2.40-2.75 (4 个 episode), val 2.04-2.29 (5 个), src 探针 -1.29..2.54 (6 个有效, 1 个无效输出); 已发表 [源 g2.md, 2211.08553, 2309.02612]: UMX 5.33/UMXHQ 5.41/UMXL 6.32, HT-Demucs 7.52(仅 MUSDB)/8.80(+800 首)/ft 9.00, BS-RoFormer 9.80, IRM oracle 8.22.
- 评分器 (museval 一致性已由 g2 验证 [源]): 我用 adapter 自带的打分函数对 IRM oracle 复算, 结果与已发表 IRM oracle 一致 (下条), 未发现打分错误; 公平性问题只有 e 项的两点 (z=1 与 norm_score 截断), 都不影响 primary dB.
- **天花板** [测, oracle22.py/agg22.py]: 本协议 IRM oracle (22.05 kHz, 6 秒, NaN 规则; 功率比掩码 / 幅度比掩码): id(150 项) 8.49 / 7.51, val(70) 8.75 / 7.77, src(128) 8.32 / 7.37; 已发表 8.22 [源]. 逐目标 id: vocals 9.79, drums 8.58, bass 7.43, other 8.17.
- **降采样** [测, oracle44c.py; 仅 3 条测试曲 x 中间 30 s, 小样本]: 44.1 kHz 直接算 7.98, 同一估计带限到 22.05 kHz 后 7.99 (带宽不是原因), 先降采样再算 (我们的路径) 8.87: +0.9 dB 来自 2048 点 STFT 在 22.05 kHz 下窗更长 (93 ms 对 46 ms), 是 oracle 的属性, 不会迁移到 Demucs. mixture 参考 -5.37 对 -5.36, 参考不受影响. 结论: 降采样不损失上限.
- **整曲中位数 vs 16 条 6 秒摘录**: 估计量相同 (帧中位数 -> 条目中位数 -> 4 目标均值). 从 150 条 id oracle 反复抽 16 条: 均值 8.57 对全体 8.49, SD 0.54 [测], 无系统偏差, 只有 +-0.5..0.8 的噪声. 未直接用整曲测 (只用 30 秒片段), 这一点是论证而非实测.
- **工具箱学习曲线** [测, lcurve2.py, 24 条 id 评测项, 默认超参, 训练摘录来自不同曲目]: 8 条 2.22/1.90 (两次抽样), 16 条 2.47, 32 条 2.70; 每翻倍约 +0.2..0.4, 外推到 100 首整曲约 3.2-4 [估], 仍低于 UMX 5.3. 逐目标 (32 条) vocals 2.85/drums 4.85/bass 1.96/other 1.13, 对 UMX 6.32/5.73/5.23/4.02 [源]: drums 差 0.9, 其余差 2.9-3.5 dB.
- **agent 轨迹** [测, traj_brief.py]: final_a0 id-00: 15 步, 默认 `separate()` dev 3.287 -> 三组超参 3.305/3.366/3.347 -> 选 3.366 结束; val-00: 2.703 -> 2.746 共 10 步. 只用了 `separate()` 的 4 个超参, 从未调用 cross_validate/gain_only/oracle_mask_sdr/sdr_scores, 也没有把 4 条 dev 并入训练 (约 +0.2..0.4 [估]). 超参差 0.02-0.08 dB, 远小于 4 条 dev 的噪声 (dev 3.37 对 eval 2.75, 高估约 0.6), 所以调参没有信息. 提前收手的原因: z=1 的门槛 = mixture 参考 + 3 dB, 约 -2.8 dB, 第一次打分 (+3.3) 就超过 6 dB.
- **e) z=1 无信息**: 16 个 FoR36 episode 中 15 个 z=1 (含 -1.29 dB), 唯一 z=0 是无效输出; 门槛 -2.8 dB 对已达 2.4-2.75 有 5 dB 以上余量. `norm_score`=10^((p-ref)/10) 截断在 10 (NORM_CLIP), 即 p >= ref+10 约 4.2 dB 就饱和: UMX(5.3) 与 HT-Demucs(8.5) 都会得 10, 论文必须报 primary dB, 或改截断 (adapter 改动, 不在本次范围).

## 3 INTEGRATION DESIGN
- **函数**: `scilib/audiosep.py` 新增 `separate_pretrained(mixtures, model="htdemucs", device="auto", shifts=0)`, 输入 (k,n,2) float @22,050 Hz, 输出 float32 (k,4,n,2), 顺序 vocals, drums, bass, other (Demucs 原生顺序是 drums, bass, other, vocals, 必须按 [3,0,1,2] 重排). 步骤: `resample_poly` 上采样到 44.1 kHz -> 按 Demucs CLI 做整段归一化 (减均值, 除标准差, 事后还原; apply_model 本身不做) -> `apply_model(model, x, shifts=0, split=True, overlap=0.25)` -> 下采样回 22.05 kHz 并对齐到 132,300 点. 6 秒摘录小于 7.8 s 训练段, 单段处理 (自动补零). `umxhq` 分支: 4 个 OpenUnmix 目标模型 + Wiener 滤波 (niter=1), 用本地 .pth 构造, 不走 torch.hub (worker 禁网).
- **权重路径**: 沙盒只透传 PATH/LANG/LC_*/TZ/SYSTEMROOT, HOME 被改到工作目录, 自定义环境变量不会传到 worker (runtime/sandbox.py:37). 所以 scilib 依次尝试: `SCILIB_MODEL_DIR` (需把它加进 `_ENV_PASSTHROUGH`, 一行改动, 需要 owner 批准) -> `/leonardo_scratch/large/userexternal/rqian000/models/demucs|openunmix` -> `/Users/admin/Datasets/ScienceClaw-rebuild-20260928/models/...` (本机). 用 `get_model("htdemucs", repo=Path(dir))`, 该目录放 `htdemucs.yaml` 与 .th (Demucs 会校验文件名里的 sha256 前缀). 不放 home.
- **torch**: worker 用 `sys.executable`, 所以必须装进运行 ScienceClaw 的解释器 (本机 repo `.venv`, 集群在 /leonardo_scratch/fast/AIFAC_F02_774/rqian000 下的 venv, 登录节点联网安装, 计算节点无网). 安装需要 owner 批准. integrity.py 只禁止 agent 代码里的 torch.hub/网络/subprocess/os.environ, scilib 内部调用不受影响.
- **运行时** (本机没有 torch, 无法实测, 全为 [估]): Demucs README 称 CPU 约 1.5x 音频时长 [源]; 16 条 x 7.8 s(补零后) = 125 s 音频 -> 多核约 190 s; 沙盒把 OMP 线程强制为 2, 可能慢 2-4 倍 -> 380-760 s, 对 MAX_NODE_S (默认 300, FoR36 覆盖为 600, executor.py:67 与 for36_musdb.py:569) 有超时风险. 对策: A100 上 (`torch.cuda.is_available()`) 全部 16 条约 10-20 s 含载入; CPU 上在 scilib 内 `torch.set_num_threads(min(8, cpu))`, 并把 SCIENCECLAW_MAX_SUBPROCS 降到 2-3. umxhq 在 2 线程下 16 条约 20-40 s. 每个 code 节点是新进程, 模型每次重新载入 (84 MB, 约 1-3 s), agent 的 dev 打分 (4 条) 约 1 分钟 CPU, 总墙钟 (2400 s) 足够.
- **内存**: htdemucs CPU 每个 worker 约 2-3 GB, GPU 3-7 GB (README 3 GB 起 [源]); 6 个并发 worker 最坏约 18 GB, 故 CPU 运行降并发. 复现性: 结果里有 `reproducible` 检查, GPU 浮点非确定性是否会触发, 需先读 executor 的重放容差 (未核实).
- **objective / describe 文本 (F5)**: 只陈述事实, 不写参考方法和验收门槛. 在 `scilib.describe('audiosep')` 增加: "`separate_pretrained(mixtures, model='htdemucs'|'umxhq')` 运行预装的神经分离器 (在公开多轨音乐数据上训练, 权重本地, 无需网络), 输入为交付的 22.05 kHz 混音, 输出 (k,4,n,2), 顺序 vocals, drums, bass, other; 参考耗时约 X 秒/条; 该模型的训练数据可能包含本 episode 的可见训练/dev 摘录, dev 分数因此可能偏高". 不要写"参考=混音"或"+3 dB".
- **agent 的角色**: 选择模型/按目标选模型 (dev 上比较), htdemucs+umxhq 逐目标加权集成, 用可见摘录训练的 SoftMaskSeparator 做残差校正/软掩码后处理, 判断何时停止, torch 不可用时回退到经典 `separate()`. 经典函数保持不变, 便于做"工具关闭"消融.
