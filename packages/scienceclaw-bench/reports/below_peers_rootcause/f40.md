口径: 只评"开工具"版本。src/val 只用于开发选型; id 池按预先写定的流水线**只评一次**, 没有据此再调参(`shipped_eval.py` 文件头在看 id 之前写定; id 片段在配置固定前没有被读过)。

## 0. 结论
- 工具: 新增 `scilib.audioenc`(AST-AudioSet 与 CLAP-HTSAT 的片段级嵌入; 沙箱没有 torch, 走文件中转桥到 Node0015 的 GPU 2, 白名单 `audioenc.embed`)与 `anomsound.embedding_scores`(在 L2 归一化嵌入上给出 `nn_train / nn2_pool / nn_pool / lof` 四个原始异常分, 与 `component_scores` 同一套"支持集 + 其他探针"的池约定)。默认的 log-mel 集成**没有改**, 嵌入工具只在 `audioenc.available()` 为真时才出现在目标文本里, 由 agent 决定用不用。
- **预先写定的流水线**(看 id 之前固定): 对 AST `pooled` 与 CLAP `pooled` 各算 `nn2_pool`, 取两者 rank/n 的均值, 不含 log-mel 成员。官方池化分数(每台机器 3 个值, 7 台机器共 21 个值取调和平均)[实测]:

| 队列 | 片段数 / 机器 | 新流水线 | 现有 log-mel 集成 | 差 (95% 分层配对 bootstrap) |
|---|---|---|---|---|
| src(开发) | 30 | 0.6457 | 0.4500 | +0.1958 (+0.1209, +0.6594) |
| val(开发) | 30 | 0.5174 | 0.5328 | −0.0155 (−0.1327, +0.1239) |
| **id(评测, 只评一次)** | 20 | **0.5592** | 0.5473 | **+0.0119 (−0.1531, +0.1734)** |
| id, harness episode(每台机器 16 片段, 共 7 个) | 16 | 0.5923 | 0.5467 | +0.0455 (−0.3065, +0.5482) |
| src + val + id 三队列均值 | — | 0.5741 | 0.5100 | **+0.0641 (−0.0118, +0.2346)**, 3 个队列中 2 个更好 |

  **读法**: 平均值向好, 但区间都包含 0。增益主要来自 src(现有集成在 src 上只有 0.450), val 持平略降, id 为小幅正向。调和平均对 21 个值里最弱的几个极其敏感, 每个层(域 × 正常/异常)只有 5–10 个片段, 单台机器的 AUC 抖动很大(见 §4 的逐机器表), 所以这个工具的效果**不能说显著**, 只能说"没有变差, 平均更好"。[实测]
- 对同行(`reports/overnight_20260930.md` §11): DCASE 官方基线 dev ≈ 0.55, 榜首 ≈ 0.66–0.67。我们池化分数 0.52–0.65(随队列), id 0.56–0.59, **与基线同量级, 低于榜首**。协议不同: 同行用整台机器的全部评测集(每个 section 200 个片段)与约 1000 个训练片段(并在其上训练/微调), 我们每台机器只有 20–30 个探针片段和 24 个正常支持片段, 不微调, 所以不能直接判胜负。[估计]
- 工具链端到端核对 [实测]: 用最终发布的 `scilib.audioenc` 在服务器上重算全部 728 个片段的嵌入, 与开发时用的表**逐位相同**(最大绝对差 0); 通过真实中转桥跑两个 id episode(ToyCar 12 s 与 bearing 10 s, 各 24 支持 + 16 探针, AST 与 CLAP 各一次调用), 嵌入、分数与官方 AUC/pAUC 与查表**完全相同**(差 0)。
- **Agent 端到端 episode**: 因网关 502 未得到结果, 见 §3。

## 1. 为什么加这个工具(根因)
现有的 `scilib.anomsound` 只有手工 log-mel 统计(每个 mel 带的均值/标准差、最大值、分位数)上的 kNN/LOF/马氏距离, 全部只用每台机器的 24 个正常支持片段, 不含任何预训练声学表征。首次射击(first-shot)场景下没有标注的异常, 好的"正常声音"表示就是唯一信号。榜单上靠前的系统多用预训练音频编码器提特征再做 kNN / 高斯 / 输出头式打分 [估计, 未逐个核对论文]。开发队列(src + val, 每台机器 30 个探针片段)上单个嵌入的 `nn2_pool` 已经高于 log-mel(`scripts/f40/dev_eval.log`, [实测]):

| 打分(src / val / 均值) | |
|---|---|
| log-mel `nn2_pool` | 0.4748 / 0.5263 / 0.5005 |
| 现有 log-mel 集成(默认成员) | 0.4500 / 0.5328 / 0.4914 |
| AST `pooled`(L2) `nn2_pool` | 0.6257 / 0.5099 / 0.5678 |
| AST AudioSet `logits` `nn2_pool` | 0.6161 / 0.5319 / 0.5740 |
| CLAP `pooled`(L2) `nn2_pool` | 0.6398 / 0.5116 / 0.5757 |
| **AST pooled + CLAP pooled 的 rank 平均(预先写定)** | **0.6457 / 0.5174 / 0.5816** |

## 2. 工具与选型(只用 src / val, id 片段在配置固定前没有被读)
- 嵌入: AST(`MIT/ast-finetuned-audioset-10-10-0.4593`, fp16)取最后一层归一化后 CLS 与蒸馏 token 的均值(`pooled`, 768 维)与 527 维 AudioSet logits; CLAP(`laion/clap-htsat-unfused` 音频塔, fp32)取 `pooled`(768)与投影(512)。片段重采样到模型采样率(AST 16 kHz / CLAP 48 kHz), 超过 10.24 s / 10 s 时取首尾两个窗口取均值。
- 打分: 嵌入 L2 归一化后的欧氏距离; `nn2_pool` = 在 {24 个支持片段} ∪ {同一台机器的其他探针片段} 中的第二近邻距离(自身排除; 与 `component_scores` 同一约定, 不用任何标签)。
- 探索过的方向 [实测]: AST 逐帧(patch)打分与多层(4/8/10/12 层)特征 —— 最好的逐帧配置 0.5522, 低于 AST 片段级(0.5678), 放弃(`scripts/f40/frame_eval.head.log`); 嵌入与 log-mel 成员的 rank 融合 —— 加 log-mel 的权重后开发均值下降(0.5816 → 0.5669, `combo_eval.log`), 所以流水线不含 log-mel 成员。
- **选定**: AST `pooled` + CLAP `pooled` 的 `nn2_pool` rank 平均。注意这是**先验选择**而不是开发集上的最大值: `combo_eval.log` 里更靠前的组合(0.5835 等)与它只差 0.002, 在噪声内, 我们没有挑最大值。开发队列上相对现有集成的配对区间 (+0.0243, +0.3411)。
- 默认值**没有改**: 不改 `fit_predict` / `DEFAULT_MEMBERS`, 嵌入工具是附加库; 文档(`docs/tasks/FoR40.md`)与目标文本只写函数、训练语料与耗时, 不写目标值、阈值、推荐配方(`tests/test_scilib_audioenc.py`、`tests/test_adapter_visible_text.py` 断言)。
- 成本 [实测, 发布的代码, GPU 2]: AST 120–140 片段/s, CLAP 28 片段/s(32 片段一批, 10–12 s 片段); 经桥的一次调用(24 + 16 片段)每个模型约 25–32 s。波形行是 float32 (1, n_samples), 每行一个桥块; `scripts/f40/prestage_blobs.py` 在服务器上由已暂存的 WAV 直接生成这些块, 不需要经 60 KB/s 的上行线路上传(728 个片段的块哈希与适配器自己读出的数组逐一核对: 0 处不一致, `check_blobs.py`)。

## 5. 披露(预训练数据重叠)
- AST(`MIT/ast-finetuned-audioset-10-10-0.4593`)由 ImageNet 训练的 DeiT 初始化, 在 AudioSet(约 200 万个 10 秒 YouTube 片段, 527 类)上微调; DCASE 机器声音与 AudioSet 的重叠**无法排除**。CLAP 音频塔(`laion/clap-htsat-unfused`)在 LAION-Audio-630K(633,526 个音频-文本对)上训练, 模型卡没有列出其他数据集, 重叠同样无法排除。两个模型都没有见过本基准的标签; DCASE 2024 开发集是公开数据(Zenodo 10902294)。
- 重建的队列(30 / 20 个探针片段/机器)是数据组的冻结划分, 不是论文的原始样本 id; 评测集是 DCASE 2024 开发数据的子集。

## 6. 剩余 / 局限
- 效果不显著(§0): 嵌入 kNN 把池化分数从约 0.51 抬到约 0.57, 但区间含 0; 想要明确区分方法好坏需要更大的探针队列(每台机器远多于 20–30 个片段)或整台机器的全部评测集, 这需要把更多官方评测片段重建进数据包(现有 728 个片段的设计是冻结的)。
- 与榜首(≈0.66–0.67)的差距主要来自: 只有 24 个支持片段(官方有 ≈1000 个训练片段)、没有目标域训练片段、不微调。若要继续, 方向是对嵌入做轻量的无监督适配(例如以支持片段拟合的白化/高斯模型), 但 24 个片段下协方差估计不稳定, 开发队列上 `maha` 类成员并不占优。[估计]
- 单个 episode 的验收(16 个片段 + 参照 + 0.02)仍受小样本噪声限制, 与本工具无关(见 `reports/overnight_20260930.md` 里"验收噪声是独立于方法的上限"一条)。
