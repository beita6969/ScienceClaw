## 0. 结论
**没有 bug, 是能力 + 协议差异。** 计分器与官方 conll18_ud_eval 对齐到 6 位小数(此前 cross-check); 我用同一 `scilib.udparse` 在整池上重训重测(不碰被评句), n=1000 时 id 池均值 0.730、src/val 池 0.777、ood(PUD) 0.718 [实测, 5 seeds, SD 0.002-0.005], 与 episode 里的 0.714-0.776 完全吻合 → 分数就是工具本身的能力, agent 轨迹没有额外损失。
对比 peers 的 93.2 是**苹果对橘子**: peers 用 14.5k 句训练 + 预训练编码器 + 更新版(更干净)标注; 我们用 ~1000 句 + 纯 numpy 一阶线性模型, 且对 2.2 旧标注评分。

(a) 协议差异: 见上表首行——训练量 1000 vs 14554 句是最大单项(≈+10, 占到"可达 0.90"的差距 17 点里的 ~58%)。peers 数字是新版标注(2.4-2.7 SUD 重转换后), 对我们的 2.2 金标估计再掉 2-4 点 [估计]。CoNLL18 冠军 86.9(GSD)/87.9(PUD) 是**同为 2.2 标注、同一 test 句子**、raw text 输入 [源:g4.md], 是最公平的锚点。
(b) 缺预训练骨干: 全量下只值 +2.3, 但**少样本(~1000 句)下价值远大于此**——词表外率(小写 form 未见于训练)test 18.6%/dev 20.6%/PUD 21.3% [实测]; 顺序不同分解会变(数据量与表示不可加)。
(c) 工具弱点 [实测, n=1000, test]: UPOS 94.2%(peers ≥97.5%); 给金标 UPOS 后 LAS +5.2(dev +5.0; n=2000 时 +3.8/+3.75) → tagger 是硬伤; UAS 0.781 vs LAS 0.730, 给金标 head 时标签准确率 0.918 → **head 归属错误(22%)是主因**, 标签错误只占 ~8%。丢分最多的关系(占全部错误, n=2000, test): punct 18.8%(召回 0.59→0.64, 占词 12.2%; 一阶局部特征学不会标点挂谁), obl 8.7%, nmod 7.1%, conj 7.0%(召回 0.45-0.48), advmod 5.5%, nsubj 5.5%, root 4.6%, fixed 4.4%(0.35-0.40), acl 4.4%, advcl/ccomp 召回 0.27-0.33。按 UPOS: NOUN 25%/PUNCT 19%/VERB 15% 的错误; DET(0.96)/ADP(0.90) 几乎无损。PUD 同型且更差(punct 召回 0.52-0.53)。
学习曲线 [实测均值; dev / test / PUD]: n=250 .701/.648/.650; 500 .743/.691/.688; 1000 .777/.730/.718; 2000 .804/.764/.737 (UPOS test .908/.927/.942/.952)。每翻倍 test +4.3/+3.9/+3.4(逐级递减), dev +4.2/+3.4/+2.7, PUD +3.9/+3.0/+1.9。外推 [估计]: n=4000 dev .83 / test .79 / PUD .75-.76; 全量 dev .85-.86 / test .82-.84 / PUD .77-.80(对数线性外推给 .877 明显过高, 舍弃)。
异常 [实测]: PUD 上给金标 UPOS 反而 LAS 从 .718 降到 .686。数据检查(`pudconv.py`, 无训练)显示 PUD 有 936 个词(占 3.8%)金标为 VERB 而 GSD 训练多数标为 AUX, 347 个 PRON 对 DET → **PUD 与 GSD 的 UPOS/关系约定不同**(deprel 每词多数票: GSD test .719 / PUD .700), ood 池有内生约定偏移, 与 CoNLL18 冠军 PUD 反而更高(87.9)并不矛盾(预训练模型不吃 UPOS 特征)。
(d) agent 轨迹 [实测, 前段]: 走推荐 API, 在 dev 切片上调 ≤3 个变体, 无预算耗尽; eval 与 dev 的差异属切片噪声(16 句 ≈300 词, SE≈0.03)。(e) 无计分 bug, 无泄漏; 唯一"不公平"是拿新版标注 + 大训练量的 peers 数字和本协议直接比。
数据清洁度 [实测, 2.2 本地文件]: train∩dev 1 句, train∩test 0, dev∩test 1, 任一∩PUD 0; 重复句 train 内 103/dev 内 2/test 内 0 (现代版 v2.3 去重: train 14449/dev 1476/test 416)。

## 3. INTEGRATION DESIGN
- 新模块 `scilib/udparse_pretrained.py`(需在 `scilib/__init__.py` 文档里声明为**唯一"读权重文件"的例外**, 现有约定是 "read no files, open no connections"; 只读、不联网、不写)。接口: `available() -> dict`(torch/stanza/权重是否在), `parse_gold_tokens(sentences, backend="stanza"|"udpipe1") -> list[{"head":[..],"deprel":[..],"upos":[..]}]`, 输入输出形状与 `UDParser.parse` 一致(输入用 `sentence_dict(s, False)` 的句词表)。`describe("udparse_pretrained")` 给出事实性 docstring。
- 输入用 **gold 词(句法词)序列**: Stanza `Pipeline("fr", processors="tokenize,pos,lemma,depparse", tokenize_pretokenized=True, download_method=None, dir=<models>/stanza_resources, pos_model_path=..., depparse_model_path=..., lemma_model_path=..., *_pretrain_path/charlm 路径)`; pretokenized 时不加载 mwt(源码 `maybe_add_mwt=not tokenize_pretokenized`), 因此 MWT("du"=de+le)已由数据的词级切分承担, HEAD/DEPREL 逐句法词输出, 与计分完全兼容; 输出 deprel 取 ':' 前的 universal 部分(计分本来就忽略子类型)。Stanza depparse 需要 tokenize+pos+lemma(源码 REQUIRES_DEFAULT), 故 lemma 模型不可省; 结果为单根树(Chu-Liu-Edmonds), 通过 `tree_issues`。
- 权重: 目录 `/leonardo_scratch/large/userexternal/rqian000/models/stanza_fr_1.14/`(Stanza 文件+`resources.json`)与 `.../models/camembert-large/`; 环境变量 `SCIENCECLAW_MODELS`。**沙箱 `_ENV_PASSTHROUGH` 不传自定义变量, 且 HOME=work 目录、HF_HUB_OFFLINE=1** → 必须(i)把该变量加入 passthrough, 并(ii)在模块里给出上述硬编码默认路径, 函数内于 import transformers 前 `os.environ["HF_HOME"]=<models>/hf`。风险点[未验证]: checkpoint 内的编码器名是 `camembert/camembert-large`, 离线需按该 repo id 布置 HF cache(或同时建 `models--camembert--camembert-large` 与 `models--almanach--camembert-large`)。绝不放 home。
- 环境: 代码节点解释器需装 `torch`(沙箱 `_PACKAGE_CANDIDATES` 已含 torch, 本机 repo .venv 没有 torch/transformers)、`stanza==1.14.0`、`transformers`、`peft`、`protobuf`、`emoji`、`networkx`、`udtools>=0.2.4`、`huggingface-hub`、`safetensors`; 版本组合我未验证, 须在计算节点用 1 个小作业实测(需先问 owner, 会耗共享预算)。Fallback 只需 `ufal.udpipe`。

## 6. 可训练变体 vs 直接用预训练解析器(诚实框架)
- 可训练变体 `scilib.udparse_plm`: 冻结 CamemBERT-base(末 4 层平均, 首子词池化)+ BiLSTM/biaffine 头, 仅用可见 ~1000 句 2.2 训练; 四个池全部**干净**(无外部解析器标签), agent 保有实质角色(选层/超参/dev 选择/tag 融合)。估计 id LAS .85(.80-.88)。CPU 2 线程上 base 编码器提特征 ~1300 句约 3-5 分钟[估计], 头训练 1-3 分钟, 需拆成"提特征→训练解析"两个节点并经节点输出传数组; **微调编码器在 CPU 节点不可行**(估计每 epoch >10 分钟), 需要 GPU 可见的节点(沙箱当前无 GPU 相关处理, 未验证)。工程量最大、结果未测。

- 建议: 先上 Stanza 作为"工具增强"条件(fallback UDPipe 1.2 保证无 torch 环境也能提升到 ≈.84); 保留现有从零学习作为基线臂; 若论文需要保留"从可见数据学习"语义, 再做可训练变体并单独报告。

- id 距 peers(~.90-.91)约 1 点; ood 反而比基线低 1.7 点。原因不是 bug: PUD 与 GSD 的标注者约定不同, 适配到 GSD 会推高 id、拉低 ood; CoNLL 2018 fr_pud 的公开最好成绩约 .84-.87, 我们 .8395 处于该范围低端。
- 在 dev 上的稳健性: 不同 1000 句子样本 .916-.921。
- 试过但不采用: (a) LightGBM"约定层"(dev .913, id .887/.868, ood .835/.863 —— 收益被微调覆盖, 已从仓库移除); (b) 微调/原权重线性插值(blend 0.5)大幅削弱域内收益, 已删除该选项(同时避免把按 PUD 调出的信息写进 agent 可见文档)。
- 工程坑(写进 `finetune` 的实现): Stanza 1.14 的 `parser.py train()` 即使 `--continue_from` 也会从训练数据重建词表, 导致标签/嵌入索引越界(CUDA assert), 所以改用 `Trainer.load` + 检查点词表 + `DataLoader(vocab=trainer.vocab)` + `InfiniteBatch` + `trainer.update`; 新版 GSD 标签集没有 `expl`、`nmod:range`, 训练标签经 `_closest_label` 映射(精确 → expl 启发式 → 基础标签 → 同基础首个已知标签 → dep)。
- 披露: Stanza 的 GSD 权重见过 UD-French GSD 的 train/dev(id 池 = test 句子不在其中); 论文里 tool-ON 结果需同时注明该重叠与 ood 折损。
