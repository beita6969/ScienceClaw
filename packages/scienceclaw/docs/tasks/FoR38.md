## Items, pools, splits
* **Targets** = positive level indicators only: `NY.GDP.PCAP.KD` GDP per capita (constant 2015 US$) and `SL.UEM.TOTL.ZS` unemployment (% of labour force, modelled ILO estimate). `NY.GDP.MKTP.KD.ZG` (GDP growth) and `FP.CPI.TOTL.ZG` (CPI inflation) cross zero, where sMAPE is ill-defined, so they are visible **covariates** only.
* **Item** = (economy, target indicator): input 1990–**2021** (NaN = not reported), target the four values **2022–2025** (horizon 4). Eligible: non-aggregate economy, 2021 value present, ≥ 20 values in 1990–2021, all 4 targets present, all values > 0. Id `WDI:<ISO3>:<indicator>:origin2021:h4`; lineage group = economy.
* **IID pool** = economies of Europe & Central Asia, East Asia & Pacific, Latin America & Caribbean, North America (122 economies, 224 items). Economies are hash-ordered with the partition seed and assigned **whole** to val (≥ 32 items), id (≥ 64), rest src (128).
* **OOD pool** = Sub-Saharan Africa; Middle East, North Africa, Afghanistan & Pakistan; South Asia (75 economies, 141 items) → `ood_kind = "proxy_within_dataset"` (regional shift).
* Economy-disjoint; partition fixed, independent of episode seeds. Capacity: src 8, val 2, id 4, ood 8 episodes.

## Visible data and tools (D_E) — anonymised view
No value after the 2021 origin is returned by any tool. **The policy-facing view is anonymised (review finding LEAK-6)**: the targets are public World Bank statistics, so a policy that recognised the economy, the indicator and the calendar years could recall the 2022–2025 values from pre-training instead of forecasting them.

| what the policy sees | instead of |
|---|---|
| economy id `E000`… (a partition-seed hash permutation of **all** non-aggregate economies, so neither alphabetical order nor eligibility is leaked) | ISO3 code and country name |
| indicator kind `T1`/`T2` (targets: a strictly positive level series; a percentage in (0, 100]) and `C1`/`C2` (covariates: annual percentage changes, may be negative); `indicator_kinds` gives these one-line descriptions | WDI codes, names, unit of account |
| periods relative to the origin: columns `t-31`…`t0` (`t0` = last observed period), `time_offsets` = −31…0, `target_offsets` = 1…4; the dev backtest uses offsets −27…0 relative to the dev origin | calendar years, "1990", "2021", "WDI vintage of July 2026" |
| coarse `region` and `income_level` (groups of tens of economies; the OOD split is defined by region) | – (kept) |
| objective, tool descriptions, constraint texts and tags say "annual country-level series"; no "World Bank"/"WDI"/"GDP"/"unemployment"/"inflation" | dataset and indicator names |

Hidden side unchanged: item ids (`WDI:<ISO3>:<indicator>:origin2021:h4`), lineage, payloads, metrics (`smape_gdp_per_capita_pct`, `smape_unemployment_pct`), reference and the manifest hash are the real ones (`lineage["anonymised_view"]` records the kind map). The item and economy partition is untouched.

| tool | returns |
|---|---|
| `load_train` | panel (560 rows = 140 IID-region economies × 4 kinds; columns `economy_id`, `region`, `income_level`, `indicator`, `t-31`…`t0`), sorted by opaque id; `indicator_kinds` |
| `load_dev` | backtest inputs: each item's history (offsets −27…0 rel. to the dev origin), `time_offsets`, `target_offsets`, metadata |
| `score_dev(pred)` | mean sMAPE of `pred` (16 × 4) against the items' next four visible periods (items with a gap are skipped) + the reference's dev score |
| `load_eval_inputs` | `history` (16 × 32), `time_offsets`, `target_offsets`, `covariates` (16 × 4 kinds × 32 periods), `covariate_indicators`, `economy_id`, `region`, `income_level`, `indicator` |

**Residual memorisation risk (not removable without destroying the task).** Opaque ids and relative time hide the *label* of a series, not its *shape*. A model that has memorised WDI can in principle still identify a series from numeric fingerprints: GDP-per-capita levels of well-known economies, the length of the history (32 periods, so the first period is 1990), the size and position of the 2009 and 2020 shocks (the COVID year is `t-1`), region and income group. FoR38 results should therefore be reported as *potentially contaminated* (pre-training cut-off after the vintage of the 2022–2025 values), and any FoR38 gain that is not confirmed on the OOD split or on FoR31/33/35/37/41 should be read with that caveat. Eliminating the risk needs a forecast origin past the model's knowledge cut-off (a later WDI vintage) — recorded as a data-team item, not done here. The anonymisation is checked by `tests/test_task_for38.py::test_visible_view_is_anonymised` (no ISO3 code, country name, indicator code/name, source name or calendar year in `public_view()` or any tool output).

## Metric, reference, acceptance (D_V)
* **sMAPE** (M4 definition) per item: `200/4 · Σ_h |y_h − ŷ_h| / (|y_h| + |ŷ_h|)`; primary = mean over items; per-indicator means also reported.
* **Pooled metric**: mean sMAPE over all items.
* **Reference**: naive / no-change forecast `ŷ_h = value(2021)`.
* **Acceptance**: mean sMAPE ≤ 0.97 × reference (3 % margin; macro series are notoriously hard to beat the random walk on).
* **Hard constraints**: `output_shape` (16, 4), `finite`, `physical_range` (y ≥ 0; unemployment rows ≤ 100 % i.e. the visible percentage kind; GDP-per-capita rows ≤ 10 × historical max i.e. the visible level kind), `declared_unit` (`native`).
* The reference recipe and the acceptance rule are **not** part of the objective or any visible text (review finding F5); they live only in `EvalResult.details` and in this document.
* **Calibration** (not a research result): reference mean src/val/id/ood = 15.6/12.5/17.6/12.0 %; a 5-year drift (GDP pc) / 3-year mean (unemployment) forecast scores 14.4/13.6/17.3/11.2 % and is accepted on 5/7, 0/2, 3/4, 3/4 episodes.

## Domain library (`scilib/macro.py`)
The episode objective ends with `scilib.describe("macro")`, the module docstring. Single entry point `fit_predict(train_panel, history, indicator, indicator_kinds=..., covariates=..., ...)` returning an (items x 4) forecast of the levels at offsets 1..4. Inside: (1) kind roles (`level` / `percent` / `change`) taken from the `indicator_kinds` descriptions, else from the value range (kind names are hash-permuted per partition seed and are never hard-coded); (2) a pool of windows from the panel and from the evaluated items' own histories (no value after the origin exists anywhere); (3) nine members on log-ratio targets `ln(y[t+h] / y[t])`: `flat`, `drift`, `robdrift` (median of the last 10 log-changes, 40 % pulled to the pool median, phi 0.9), `revert`, `theta`, and the pooled per-(kind, horizon) models `ridge` (alpha 1000, all features including the other kinds' rates), `lgbm` (all features), `huber` (Huber regression, alpha 1) and `lgbm_core` (L1 LightGBM, 150 trees, 8 leaves, min 40 rows) on the eight own-series "core" features (g1, g3, g8, dev3, dev10, devall, vol, ln y); (4) block-level helpers: `member_forecasts`, `local_forecast`, `rolling_backtest`, `fit_weights` (SLSQP on the tanh form of sMAPE, optional shrink toward equal weights), `smape_logratio`, `period_profile` (cross-economy median / MAD of the annual change per period). **Default members `("ridge", "huber", "lgbm_core", "robdrift")`, equal weights** (one call, no tuning needed); `weights="auto"` fits weights on an 8-origin rolling backtest (origins spaced one period apart, newest = horizon periods before the last one, fitted weights mixed 50:50 with equal weights); `fit_predict` accepts every member name; `return_info=True` adds `backtest_origins`, `backtest_smape` (pooled) and `backtest_by_origin` per kind. Percent kinds are clipped to (0, 100]. Deterministic (seeded), 2-3 s for 16 items (with the backtest ~3 s), no files / network. The docstring states sMAPE facts (the `tanh` form, the log-ratio equivalence), the member list with parameters, what the dev split and the backtests cover (one origin, targets = the last observed periods, common shocks) and that the defaults were chosen from rolling-origin backtests of the visible panel; it states no reference, margin or recommendation (F5) and avoids the words scanned by `tests/test_adapter_visible_text.py`.
* **Measured** (library level: `fit_predict(load_train, **load_eval_inputs)` on stored episodes, partition seed 20260928, 23 episodes; pooled sMAPE ratio to the no-change reference, accepted = ratio <= 0.97): new default src 0.841 (7/8 accepted; level kind 8.81 -> 6.43, percent kind 21.46 -> 19.03), val 0.843 (2/2), id 0.775 (4/4), ood 0.830 (7/8), frozen full-run val episode `FoR38-val-s05ad886f-e00` 0.937 (12.28 vs 13.10). Old default (`ridge` + `lgbm`, equal): src 0.905, val 0.885, id 0.809, ood 0.902, frozen val 0.966 (12.66, a thin pass). The two misses (src e02, ood e02) are on the percent kind (ratio 1.07 / 1.05); 16 items per episode with ~8 unemployment items make the per-episode ratio noisy (mean 0.828, sd 0.083 over the 23 episodes, 21/23 accepted), so the expected per-episode acceptance is ~90 %. `weights="auto"` (new 8-origin version, shrink 0.5): src 0.847, val 0.860, id 0.772, ood 0.846, frozen val 0.947; the old 3-origin version (spacing 4, no shrink, ridge + lgbm) gave src 5/8, ood 6/8, frozen val 0/1 (13.21).

* **What changed**: (1) default members: the own-series-only models (`huber`, `lgbm_core`) replace full-feature LightGBM, and `robdrift` adds a robust trend; on the percent kind at the 2021 origin (pooled over all 23 stored episodes, 176 items) flat 20.63, old default 20.64, new default 18.4; level kind 8.18 / 5.87 / 5.82; on the nested backtests inside `load_train` (origins 12..26) the new default is 0.3 sMAPE points better on the percent kind and equal on the level kind, and it is better on the analogue of the 2008-09 shock (origin 20). (3) `fit_predict` accepts all block members (the agent hit `ValueError: unknown member` for `revert` / `theta`), and `info` reports per-origin scores.

In that episode the agent scored several member sets and weightings on the 16-item dev split, whose reference score (15.82) it could not beat (its scores 15.7-16.4), and kept iterating until the 200k token budget ended the run. Quality on ood/id agent runs matches the library-level numbers above.
* **Known issues**: (a) the percent kind remains the ceiling (unemployment fell 15-18 % over 2022-2025 in the sample while the members predict a change of +2 % to -7 % at step 4); a scale factor above 1 helps the evaluation origin but is neutral on the visible backtests, so it is not used. (b) The dev score is a one-origin, 16-item guide: the new default is 0.958 x flat on average over the 23 stored dev splits (old 0.960, auto 0.946), with a per-episode spread from 0.8 to 1.3, so it cannot separate the members; the docstring states what the dev split covers. (c) The defaults were chosen on nested visible backtests (origins 12..26 of `load_train`, plus the origin-20 shock analogue); the evaluation episodes were used to confirm the choice and to reject full-feature LightGBM for the percent kind, so the numbers above are somewhat optimistic. (d) Contamination through numeric fingerprints (see above) applies to any FoR38 gain. (e) Token budget: each step re-sends the objective (the `macro` docstring is ~2.2k tokens of ~9.5k per step) and the growing graph, so ~20 steps use the 200k policy tokens; an agent that chases the dev-split reference (the shock in the dev targets makes it hard to beat with any method) can run out of tokens while its submission is already accepted (1 of 7 probes, id e00 twice).

## Deviations from the historical protocol
* The original "World Bank macro forecasting64" database, vintage, indicator list, horizon and sample ids were **not recovered**; these are **rebuilt splits** on the July-2026 WDI vintage (origin 2021, horizon 4 chosen here). Historical protocol 64 IID + 64 OOD: here id = 64, ood = 64 items.
* Uses the full recorded API responses instead of the data team's 128-series selection (reason above); GDP growth and inflation are covariates, not targets.
* 2025 values are the latest (partly preliminary) WDI estimates of this vintage.
* OOD is a regional shift within WDI. **Data team:** a second macro source (e.g. IMF WEO or Penn World Table for the same economies) would allow a cross-dataset OOD pool.
