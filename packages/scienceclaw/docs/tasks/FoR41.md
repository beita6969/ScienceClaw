## Items, pools, splits
* **Item** = (site, reference date t0): input = the site's daily oxygen / temperature / chla for the **1461 days** ending at t0; target = observed daily oxygen and temperature on **t0+1 … t0+30** (the challenge horizon; unobserved days are not scored). Id `neon4cast-aquatics:<SITE>:ref=<date>:h30`; lineage group = site.
* Reference dates on a **37-day grid** from 2019-06-01 (> 30 + 7, so a target window never touches the last 7 history days of another item at the same site). Eligible: for both oxygen and temperature ≥ 10 observed target days, ≥ 60 observed days in the 365 days up to t0, and an observation within the last 7 days.
* **IID pool** = 24 wadeable-stream sites; temporal windows for t0: **src** 2019-06-01 … 2022-12-31 (all 513 eligible items), **val** 2023 (32 items), **id** 2024-01-01 … 2026-06-30 (64 items); val/id are picked round-robin over sites with the partition seed.
* **OOD pool** = the 7 lakes + 3 non-wadeable rivers, t0 in 2024-01-01 … 2026-06-30 (64 items) → `ood_kind = "proxy_within_dataset"` (ecosystem-type shift).
* **Label masking**: the 30-day target windows of all val/id/ood items are set to NaN (all variables) in every visible history of every episode; each episode additionally withholds the target windows of its own items from all of its inputs (relevant when a site occurs twice in an episode). Episodes are drawn with distinct sites where the sub-pool allows it (always for src). Capacity: src 32, val 2, id 4, ood 4 episodes.

## Visible data and tools (D_E)
The per-item site history is the training data of this task (the neon4cast setting); there is no separate `load_train`.
| tool | returns |
|---|---|
| `load_eval_inputs` | `history` (16 × 1461 × 3: oxygen mg/L, temperature °C, chla µg/L; `history[i, -1]` = t0; NaN = not observed/withheld), `variables`, `units`, `horizon_days`, `site_id`, `site_type`, `reference_date` |
| `load_dev` | backtest inputs: each item's history ending 30 days before t0 |
| `score_dev(pred)` | mean CRPS of a deliverable-format dict on the backtest targets (t0−29 … t0, visible days) + per-variable CRPS + the reference's dev score |

## Deliverable
`y = {"oxygen_mu", "oxygen_sigma", "temperature_mu", "temperature_sigma"}`, each float (16, 30): a normal predictive distribution per item and lead day (neon4cast `family = "normal"`, parameters `mu`, `sigma`); oxygen in mg/L, temperature in °C.

## Metric, reference, acceptance (D_V)
* **CRPS** of N(μ, σ²) at the observation, closed form (Gneiting & Raftery 2007; = `scoringRules::crps_norm` used by neon4cast), averaged over all observed (item, day) pairs **per variable**; primary = **equal-weight mean of oxygen CRPS (mg/L) and temperature CRPS (°C)** — the paper's prespecified scalar. The two CRPS values have different units, so both are always reported separately (`crps_oxygen_mgL`, `crps_temperature_degC`, plus observation counts); `pooled_per_variable()` gives them for pooled reporting.
* **Pooled metric**: per-variable CRPS sums and counts accumulated over all items, then the equal-weight mean.
* **Reference**: smoothed day-of-year climatology of the item's visible history (mean / sd of observations within ±7 days of the target day-of-year; sd floored at 0.1; fallback last-365-day mean / sd when fewer than 5 observations) — the neon4cast climatology null model.
* **Acceptance**: mean CRPS ≤ 0.95 × reference.
* **Hard constraints**: `output_structure` (dict with the 4 keys, each (16, 30)), `finite`, `positive_sigma`, `physical_range` (oxygen_mu ∈ [0, 30] mg/L, temperature_mu ∈ [−5, 45] °C — catches kelvin —, sigmas ≤ 50). No `declared_unit` check: the deliverable is a dict with per-key units.
* **Calibration** (not a research result): reference mean src/val/id/ood = 0.913/0.672/0.638/0.793; a persistence–climatology blend (weight e^(−lead/10)) scores 0.789/0.605/0.591/0.732 and is accepted on 6/7, 2/2, 3/4, 3/4 episodes.

## Domain library (`scilib/aquatics.py`)
The episode objective ends with `scilib.describe("aquatics")`, the module docstring. Single entry point `fit_predict(history, reference_date, lam=0.75, smult=1.0, ...)` (`fit_predict(**inputs)` works for both `load_eval_inputs` and `load_dev`) returning the deliverable dict of four (n, 30) arrays. Inside, per item and variable: (1) a smooth day-of-year profile of the item's history (ridge OLS on K = 2 annual harmonics plus a shrunk, +-10-day day-of-year residual table); (2) the anomaly = observation - profile; (3) two predictors at each origin day, the mean anomaly of the last 3 days and of the last 30 days; (4) per lead 1..30 a ridge regression (penalty 1) of the anomaly h days later on these two predictors, fitted per item and pooled over the items of the call and blended `lam * item + (1 - lam) * pooled` (item fit only with >= 200 pairs at that lead); sigma = blended residual sd * `smult`, floored at 0.05; mu / sigma clipped to the physical ranges. The per-lead ridge and residual sd are computed from sufficient statistics, so the whole call takes about 1-3 s for 16 items on one core. Items with < 60 observed days of a variable fall back to `doy_window_forecast` (+-7-day day-of-year window mean / sd); no observation at all raises a `ValueError` naming the items. Other functions: `data_report` (coverage / age of the last observation per item and variable), `doy_window_forecast`, `backtest` (rolling-origin check that needs only `history`; shift 30 equals the `score_dev` window), `score`, `crps_normal`, `seasonal_profile`, `history_dates`. Pure numpy, no files / network; every function works only on the arrays it is given, and dev and evaluation inputs go through the same call. The docstring states the layout and the mechanics and the range explored for each parameter; it names no reference model, window or factor and avoids the words scanned by `tests/test_adapter_visible_text.py` (the profile is called "smooth day-of-year profile"). Tests: `tests/test_scilib_aquatics.py` (14 synthetic-data tests: format / ranges / determinism, port keywords and argument checks, date handling, `lam` / `smult` behaviour, sparse and empty items, order independence, `doy_window_forecast` equal to the adapter's window statistics, `score` equal to the adapter's CRPS), plus two tests in `tests/test_task_for41.py` (objective documents the library; the library beats the reference on a real src episode).
* **Provenance of the recipe and parameters**: the recipe and its defaults (K = 2, shrink 0.3, +-10 days, fast 3 / slow 30 days, ridge 1, lam 0.75, smult 1.0) come from the SOTA brief, where each was picked among 2-4 options on the val / id / src pools. The port reproduces `briefs/calibration/FoR41_ref_impl.py` to ~1e-15 (checked in a scratch script, not in the test suite). I re-ran the sweeps on the real adapter episodes (partition seeds 20260928, 11, 12, 13; 24 src, 8 val, 16 id, 16 ood episodes, all four pools, scored against the evaluation targets) and **changed no default**. Mean primary / reference ratio (share of episodes accepted): defaults src 0.736 (1.00), val 0.822 (1.00), id 0.900 (0.94), ood 0.903 (0.88). Sensitivity: lam 0 (pooled only) 0.768 / 0.877 / 0.918 / 0.930; lam 1 0.737 / 0.813 / 0.907 / 0.907; smult 0.8 ... 1.2 within 1-3 % of the defaults (smaller values suit val, larger ones ood); K = 1 / 3 / 4 worse or equal (K = 4 worst on src); shrink 0 / 0.6, fast window 1 / 5 / 7 and slow window 14 within 3 %; profile only (no anomaly regression) 0.824 / 0.966 / 0.978 / 0.953. "A linear trend term or a seasonally varying sigma did not help" in the docstring is the brief's measurement, not re-run here.
* **Library-level** (hand-written node `fit_predict(**load_dev)` / `fit_predict(**load_eval_inputs)` through `scripts/dev/run_node_on_episodes.py`, partition seed 20260928; accepted = primary <= 0.95 x reference): src 3/3 (primary 0.632 / 0.639 / 0.606 vs reference 1.054 / 0.819 / 0.843), val 2/2 (0.563 vs 0.699; 0.546 vs 0.645), id 3/4 (the miss: 0.6449 vs 0.6692, norm 1.038), ood 3/4 (the miss: 0.7104 vs 0.7465, norm 1.051). About 1 s per episode. On the probe partition (`se06c8e77`, seed 20260928 of `configs/dev5_local.yaml`): src 0.642 / 0.645 / 0.687 vs reference 0.852 / 0.951 / 1.083.
* **Real agent** (`scripts/probe.py --config configs/dev5_local.yaml --disciplines FoR41 --split src --n 3 --workers 2`, self-hosted 27B model, A_0, episodes `FoR41-src-se06c8e77-e00..e02`; `runs/probe_for41_scilib`): before, stock A_0 passed 1/3 with primary 1.61 / 0.98 / 0.79 (`runs/probe_pass10_n3`). With the library 3/3 accepted, primary 0.640 / 0.645 / 0.692 (norm 1.33 / 1.48 / 1.56), 16 / 9 / 12 steps, 133 k / 65 k / 90 k tokens, 80-111 s each. n = 3 per pass, so this is evidence of the mechanism, not a pass rate. A re-run returned the same numbers from the LLM cache.
* **Known issues**: (a) the agent sweeps `lam` / `smult` on the dev score (lam 0.5 / 0.75 / 1.0 and smult 0.9 / 1.0 / 1.1 across the three episodes) and ended with lam 1.0 / smult 1.0, lam 1.0 / smult 1.1 and lam 0.5 / smult 1.0 respectively; on these episodes the overrides cost at most 0.7 % against the defaults (0.6399 vs 0.6418, 0.6449 vs 0.6453, 0.6919 vs 0.6870), because the surface is flat, but the dev score is a noisy guide (b). (b) The dev target window (the last 30 days of the visible history) is partly withheld: the val / id / ood target windows are masked globally in every history, so where the previous 37-day grid point of the same site is also a pool item the dev targets are missing. Observed share of dev targets: src 0.94, val 0.93, id 0.82, ood 0.69; items with < 50 % of their dev targets observed: src 2 %, val 6 %, id 19 %, ood 36 %. Dev is therefore a noisier proxy for the evaluation score on id / ood. (c) In the multi-seed sweep 6 % of id and 12 % of ood episodes were not accepted (mean ratio 0.90); the remaining error is dominated by weather-driven temperature shocks at longer leads, and none of the parameter changes above fixed it. (d) Sites with < 60 observed days of a variable use the day-of-year window fallback; about 1 % of items have no observation in the last 3 days (the fast predictor is then taken as 0).

## Pretrained time-series models (`scilib/tsfm.py`)
`scilib.describe_extra("tsfm")` is appended to the objective only when `tsfm.available()` (local torch + chronos + weights, or the remote GPU bridge). `tsfm.forecast(histories, horizon, quantiles, model, context_length, lengths)` returns float32 quantile forecasts (n, horizon, Q) from `chronos_2` (`amazon/chronos-2`) or `chronos_bolt` (`amazon/chronos-bolt-base`); the series are forecast independently, neither model is adapted on them. The docstring is factual (inputs, outputs, quantile levels, training corpora, measured cost; `tests/test_scilib_tsfm.py`, `tests/test_adapter_visible_text.py`). Weights on the GPU host: `models/tsfm/{chronos_2,chronos_bolt_base}`; worker whitelist entry `("tsfm", "forecast")`. Pretraining overlap with Monash / Chronos Datasets / GIFT-Eval-type corpora cannot be ruled out and is stated in the docstring.
* Offline result with the pre-declared pipeline (mu and sigma = 0.5 x `fit_predict` + 0.5 x Chronos-2; full 1461-day context; mu = q50, sigma = (q75 - q25) / 1.349, sigma clipped to [0.05, 50], mu to [0, 45]; id/ood evaluated once): mean CRPS id 0.5501 vs 0.5724 (-3.9%, 95% CI -5.9% / -2.1%, 64 items), ood 0.6891 vs 0.7163 (-3.8%, CI -7.9% / +0.1%, 64 items). Details: `reports/below_peers_rootcause/tsfm.md`.
* **Option in the main library (added 2026-10-01).** Same reason as FoR35 (0 of 12 FoR41 episodes imported `scilib.tsfm`): `aquatics.fit_predict(..., pretrained=w)` returns every mu / sigma array as (1 - w) x its usual value + w x the Chronos-2 value (median clipped to [0, 45]; sigma = (q75 - q25) / 1.349 clipped to [0.05, 50]; items with < 3 observed days of a variable keep the usual value), i.e. the pre-declared pipeline for w = 0.5. `pretrained=0` (default) is the previous behaviour and makes no GPU call. Tests: `tests/test_pretrained_options.py`.

## Budget

## Deviations from the historical protocol
* The original site / date selection was **not recovered**; these are **rebuilt splits** (sites, 37-day grid, temporal windows and 30-day horizon chosen here). Historical protocol 64 IID + 64 OOD: here id = 64, ood = 64 items.
* The paper averages CRPS across variables with different units; this is kept as the primary for comparability, with per-variable CRPS always reported.
* Only normal (μ, σ) forecasts are accepted (the challenge also accepts ensembles).
* OOD is an ecosystem-type shift within neon4cast. **Data team:** a second freshwater forecasting target set (e.g. the VERA / Virginia Reservoirs forecasting challenge targets) would allow a cross-dataset OOD pool.
